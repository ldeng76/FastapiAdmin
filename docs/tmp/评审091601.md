# 评审结论：方向合理，但有 3 个阻断性问题，不能按现状直接执行

## 总评

方案的目标（KPI 语义对齐、维度切业务模态、覆盖率告知、`by_file_type`→`by_center` 改名）是对的，Step 3 的 LEFT JOIN + 未关联桶 + 覆盖率字段设计是亮点，权限层引用（`permission.py:69`、`:190`）与代码完全吻合。**但方案是基于一个不存在的代码基线写的，且 Step 1 会直接顶掉同事昨天的刻意修改**。前端侧的核对全部吻合（`index.vue:16` 确实用 `med_center` 字典、`files.ts:27` 的 `by_file_type`、`getFileType()` 遗留 bug 属实）。

## P0 — 阻断性问题

**1. Step 1 与昨天的提交 34bb4156 直接冲突，方案没有提及**

`git show 34bb4156`（“记录数显示调整”，cyh，2026-09-15 14:54，即昨天）删除的正是 Step 1 要加回的代码——按 `exam_type + center_type` 查 `AnonExamModel` 行数的 `exam_count_sql`，并把 `exam_count` 改成了 `file_count`。Step 1 的新增代码与被删代码几乎逐字相同。这说明「记录」卡片显示 file_count 很可能是产品侧的**刻意决策**（列表页的“记录”就该等于表格行数 119,350，而不是 1.5M 检查表行数），不是实现失误。方案在 Assumptions 里只提到“视觉冲击大”，没意识到这是一次昨天的反向修改。**不先和 cyh/用户确认“记录卡片到底显示什么”就执行，大概率今天改回、明天又被改回**。更合理的替代方案：保留 `exam_count = file_count`，只修 `schema.py:85` 的 description 与实现不符这一半问题；或前端把“记录”卡片语义拆开。

**2. Step 2 的前提在本仓库不存在——`size_sql` 从未有过**

当前 [service.py:156](E:\mw3\wspy\2026\lnrs\backend\app\plugin\module_medical\files\service.py#L156)/165/169 里 `total_size_bytes` 是硬编码 0（sum 被注释掉），`AnonDicomSeriesModel` 根本没导入（[service.py:15](E:\mw3\wspy\2026\lnrs\backend\app\plugin\module_medical\files\service.py#L15) 只导入 `AnonExamModel`；方案说第 16 行两个都导入了，不实）。`git log --all -S "size_sql"` 确认任何分支都没出现过 size_sql。因此 Context §3 的“权限泄露”不存在——字段恒为 0，前端显示 0 B。Step 2 的真实内容是**新增 total_size_bytes 功能**（0 → 真实字节，功能性变更），不是“修权限绑定”；“替换现有的 `cls._apply_permission(auth, size_sql)`”这句无可替换对象。Step 2 的验证脚本要自己手工构造 size_sql，恰恰旁证了它不在 service 里。

真实 caller 有 4 处：`statistics_service` 内 3 处 + `dict_file_types_service`（[service.py:125](E:\mw3\wspy\2026\lnrs\backend\app\plugin\module_medical\files\service.py#L125)，方案漏掉了它）。方案清单里列的 `page_service` 调用**不存在**——page_service 委托 `MedFilesCRUD(auth).page()`，权限在 CRUD 内部做。照方案删 helper 而只改列出的 caller，`dict_file_types_service` 会 AttributeError，前端 `onBeforeMount` 里的 `getFileType()` 直接挂，整个页面初始化报错。

## P1 — 应修问题

**4. Step 3 只修了 statistics，`/list` 的同一字典错位没处理，改完 KPI 和表格会自相矛盾。** 侧边栏 `med_exam_type` 复选框同时驱动 statistics 和列表：`page_service` 的 `search["exam_type"]` 仍过滤 `m.exam_type`（= `modality`，DICOM 模态）。改造后勾选 Pathology 会出现“统计显示 Pathology 有 N 例、表格 0 行”。至少要在方案里明确记录这个已知错位，理想是一并处理 page_service 的映射。

**5. 未关联桶的实现细节缺失且口径有坑。** `GROUP BY exam.exam_type` 产生的是 NULL 组，要输出 `value="__unlinked__"` 必须 COALESCE/CASE，方案未提；且 NULL 组会把「关联了 exam 但 `exam.exam_type` 为空」的 study 混进未关联桶，与 `by_exam_type_unlinked`（定义为 `anon_exam_id IS NULL`）口径不一致。建议 `CASE WHEN exam.anon_exam_id IS NULL THEN '__unlinked__' ELSE COALESCE(exam.exam_type,'未知') END`。另外现 SQL 的 `where(m.exam_type.is_not(None), m.exam_type != '')` 必须去掉否则未关联桶出不来，方案也没明说。

**6. 前端改动清单不完整。** 方案说前端用 `by_exam_type_unlinked / by_exam_type_total` 显示“已关联 XX.X%”，但 Step 4 的前端改动只有 `by_center` 改名——`files.ts` 的 interface 没加这两个新字段，`index.vue` 也没有对应渲染位置。照单执行的话这两个后端字段无人消费，“覆盖率告知”落不了地。

**7. `file_type` 查询参数本来就是死的。** [service.py:63-68](E:\mw3\wspy\2026\lnrs\backend\app\plugin\module_medical\files\service.py#L63) 里 `file_type` 和 `center_type` 过滤的是**同一列** `m.file_type`（= `center_code`），传 `file_type=dcm` 实际是 `center_code IN ('dcm')` 永远 0 行。方案改了响应字段名却不提查询参数的同一语义问题；Step 1 的 exam_count 悄悄忽略 file_type（结果上无害，因参数本身已死），但应写明。
