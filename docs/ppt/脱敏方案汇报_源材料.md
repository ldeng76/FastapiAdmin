## 第 5 页 · 诉求的本质：一对矛盾

**标题**：本质：一个看似矛盾的双重约束

**要点**：
- **约束 A · 不可逆**：脱敏后，外人无法还原真实病人身份（合规底线）
- **约束 B · 可关联**：系统内部，同一病人的结构化报告 + DICOM 影像，脱敏后仍要能归到同一个人（业务必需）
- 矛盾点：A 要求"切断身份线索"，B 要求"保留身份线索"——**同一个身份标识，既要抹掉、又不能抹掉**

**视觉建议**：天平图。左盘"脱敏（不可逆）"，右盘"关联（可链接）"，中间问号。箭头指向下一页"统一确定性映射 = 解法"。

**讲稿提示**：这一页是全场最重要的认知铺垫。让听众理解：这不是"做个脱敏函数"的小事，而是要同时满足两个拉扯的目标。

## 第 7 页 · 关键发现 ①：两边是同一批人

**标题**：发现 ①：DICOM 与结构化数据是同一批病人

**要点**：
- 取 2 份真实数据核对：DICOM 目录清单（70 个病人）vs `CT与病理数据.csv`（20 万行）
- DICOM 目录命名 `<PatientID>_<StudyUID>` 的 PatientID，**100% 命中** CSV 的 `PAT_LOCAL_ID` 列（70/70）
- 结论：**`PAT_LOCAL_ID` 是天然存在的跨模态统一主键**

**视觉建议**：两列对照表。左列"DICOM PatientID"列出 `1008201 / 1495303 / ...`，右列"CSV PAT_LOCAL_ID"同样值，中间绿色 ✓ 连线。底部大字"70/70 命中"。

**讲稿提示**：这是整个方案能成立的根基——如果没有这个统一主键，"统一映射"在数学上就不可能。先讲清这个事实，方案才有立足点。

## 第 8 页 · 关键发现 ②：三级 ID 与撞号风险

**标题**：发现 ②：ID 分三层，且跨中心会撞号

**要点**：
- **三级粒度**：
  - `PAT_LOCAL_ID`：病人级（一个人）← 统一主键
  - `SICK_ID`：住院级（一次住院，多次住院会有多个）
  - `EXAM_NO`：检查级（一次 CT）← 同时出现在 DICOM StudyInstanceUID，天然桥梁
- **撞号风险**：`PAT_LOCAL_ID` 是"本地号"，珠江的 `1008201` 和省医的 `1008201` 是**两个不同的人**
- 含义：哈希输入不能只取 `PAT_LOCAL_ID`，必须带上中心

**视觉建议**：上方三级金字塔（病人 > 住院 > 检查）。下方两行：珠江 `1008201` ≠ 省医 `1008201`，用红 ⚡ 标"撞号"。

**讲稿提示**：这一页解释了为什么方案里"中心"要进哈希输入——否则会错误合并两个不同病人，直接违背"归属正确"。

## 第 9 页 · 方案总览：统一确定性映射

**标题**：方案总览：统一确定性映射（Linkable Anonymization）

**要点**：
- **一句话方案**：用同一个确定性函数，对"中心 + 病人号"做哈希，生成统一的脱敏 ID，写入所有模态
- **核心公式**：`ANON_ID = "ANON_" + HMAC-SHA256(项目密钥, 中心 + PAT_LOCAL_ID)[:12]`
- **三个特性同时成立**：
  - ✅ 不可逆（HMAC + 密钥抗字典攻击）
  - ✅ 可关联（确定性：同一输入永远同一输出）
  - ✅ 无映射表（明文丢弃，不留单点失败的映射表）

**视觉建议**：中央放公式。三个特性画成三个绿色 ✅ 徽章环绕。旁边一个小对比："映射表方案"打红 ❌（单点失败）。

**讲稿提示**：这是全场核心页。慢讲公式每一项为什么在那里：密钥防暴力、中心防撞号、确定性保关联。

## 第 11 页 · 决策深挖：哈希设计（#2 #3）

**标题**：决策深挖：为什么是「中心 + PAT_LOCAL_ID」+ HMAC

**要点**：
- **为什么中心进输入**：跨中心同号隔离（珠江/省医的 `1008201` → 不同 ANON_ID）
- **为什么用 HMAC 而非裸 SHA256**：
  - PAT_LOCAL_ID 只有 6–7 位，搜索空间十万级
  - 无盐 SHA256 → 攻击者离线把所有号哈希一遍，**100% 反算**
  - 加密钥的 HMAC → 无密钥无法反算，确定性不受影响
- **密钥是唯一受保护资产**：丢失 = 永久不可逆，须可恢复备份

**视觉建议**：左右对比。左："裸 SHA256" → 攻击者拿字典秒破（红 ❌）。右："HMAC + 密钥" → 无密钥无法反算（绿 ✅）。

**讲稿提示**：强调"确定性"和"抗破解"不冲突——HMAC 同时拿到两者，这是选它的关键。

## 第 12 页 · 决策深挖：跨模态关联（#4 #5 #6）

**标题**：决策深挖：怎么把报告和片子对上

**要点**：
- **两层粒度**：
  - 病人级：`PAT_LOCAL_ID → ANON_ID`（一个人）
  - 检查级：`EXAM_NO → ANON_EXAM_ID`（一次 CT，精到"这张片子是这次检查拍的"）
- **DICOM UID 确定性重生成**：项目 OID 根 + HMAC 填充成合法 UID（不是随机生成——否则关联断链）
- **检查级桥梁**：DICOM `AccessionNumber` 标签存 EXAM_NO（标准字段，不靠 UID 命名规律这种脆弱约定）
- **浏览器不受影响**：PACS 浏览器运行时扫描磁盘重建索引，不依赖历史 UID

**视觉建议**：横向数据流图。左：CSV 行（ANON_ID + ANON_EXAM_ID）→ 中：DICOM 文件（PatientID=ANON_ID, AccessionNumber=EXAM_NO）→ 右：浏览器正常显示。三段用绿色实线串联。

**讲稿提示**：这页回答第 6 页抛的"怎么串起来"的问题。强调检查级桥梁是 AccessionNumber 这个标准字段，不是 hack。

## 第 13 页 · 决策深挖：文本与日期（#7 #8 #9 #10 #11）

**标题**：决策深挖：剩下的 PHI 怎么处理

**要点**：
- **SICK_ID（住院号）→ 清空**：夹在病人级和检查级中间的冗余粒度，少数多次住院才用，不保留
- **明文 ID → 原地替换丢弃**：项目库里不留任何明文病人号（否则等于没脱敏）；反查靠持密钥者 HMAC 重算
- **报告正文 PHI（人名/医生名/机构/历史日期）→ 规则 + 私有 LLM**：
  - 私有化部署 Qwen3，**数据不出内网**（合规关键）
  - 规则先扫确定性强的（日期、机构），LLM 兜底识别开放集合（人名）
- **日期**：检查/就诊日期原值保留；出生日期只留年份、月日清零（两侧规则一致）

**视觉建议**：四象限。每象限一个 PHI 类型 + 处理方式图标（🗑️清空 / 🔄替换 / 🤖LLM / 📅日期）。

**讲稿提示**：重点讲"私有 LLM"——这是兼顾准确性和合规的关键，因为数据不出内网，不存在"送外部 LLM = 新泄露面"的问题。

## 第 14 页 · 被否方案与权衡

**标题**：我们考虑过、但否决了的方案

**要点**（表格）：

| 被否方案 | 否决理由 |
|---|---|
| 映射表（各模态各自脱敏 + 对照表） | 映射表是**单点失败**——泄漏即重识别密钥，且需长期维护 |
| 裸 SHA256（无盐） | 病人号空间小，等同明文可逆，挡不住字典攻击 |
| DICOM UID 随机重生成 | 切断检查级关联，与"归属正确"冲突 |
| DICOM UID 原值保留 | UID 含设备序列号/时间戳/机构 OID，属可识别信息 |
| 新增 ANON 列、明文并存 | 项目库里仍存明文病人号，违背"进入前必须脱敏" |

**视觉建议**：表格，每行末尾红色 ❌。强调"每个否决都有具体理由，不是随便选的"。

**讲稿提示**：这页体现方案的严谨性——尤其应对"为什么不简单点用映射表"这类质疑。映射表看起来省事，实则是最大的安全隐患。

## 第 15 页 · 风险与后果

**标题**：风险与需知晓的后果

**要点**：
- **⚠️ 密钥是单点资产**：丢失 = 永久不可逆。上线前必须有**可恢复备份**，不能只存单机
- **⚠️ 自由文本脱敏非 100%**：规则 + LLM 仍有漏检，保留**人工抽检**兜底
- **ℹ️ 旧 Parquet 不纳入**：那批 8 位 `patient_id` 是另一批数据，本方案不覆盖
- **ℹ️ UID 替换的外部影响**：缓存了旧 UID 的外部 PACS 系统需重新索引

**视觉建议**：风险矩阵或四列卡片。⚠️ 用橙/红，ℹ️ 用蓝。每条配一个缓解动作。

**讲稿提示**：诚实交代局限反而增加可信度。重点强调密钥备份——这是上线前唯一的硬前置。

## 第 16 页 · 实施路径与总结

**标题**：下一步 · 实施路径

**要点**：
- **Phase 1**：HMAC 核心模块 + 密钥管理（配置/环境变量 + 备份）
- **Phase 2**：CSV/Parquet 脱敏器（ID 替换 + 日期规整）
- **Phase 3**：DICOM 脱敏器（UID 重生成 + AccessionNumber 写入 + PHI 标签清除）
- **Phase 4**：私有 LLM 文本清洗管线（Qwen3）+ 人工抽检流程
- **Phase 5**：端到端验证（跨模态关联正确性 + 漏检抽检）

**总结一句话**：
> 以「中心 + PAT_LOCAL_ID」的 HMAC 为统一主键，明文丢弃、无映射表，跨中心不撞号、检查级可精确对应——在"脱敏"与"归属正确"之间找到同时满足的解。

**视觉建议**：横向 5 步流程箭头。底部放大字总结句。

**讲稿提示**：收尾呼应第 4 页的核心诉求——证明方案同时满足了"脱敏"和"归属正确"这对矛盾。
