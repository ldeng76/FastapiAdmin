# 肺结节研究系统 ·「医学AI建模平台」需求确认书

> **文档性质**：需求理解与决策确认（非技术方案）
> **面向对象**：客户决策层 / 业务负责人
> **生成日期**：2026-07-01
> **关联背景**：客户基于 UCSC Xena（基因组数据探索平台）提出了"模型使用模块"的四部分（A-D）功能设想，本文档旨在确认我方对该设想的理解，并就需要客户拍板的关键问题进行澄清。

## 一、我方对需求的理解

### 1.1 总体定位

综合两轮信息（Xena 平台截图 + A-D 四部分描述），我方理解客户希望将本系统从「肺结节数据的**后台管理系统**」升级为「面向医学研究者的**多模态 AI 建模实验台**」——即一个内置医疗数据、Python 环境、算法模板的可交互研究平台。

参照系可概括为：

> **[数据浏览器（Xena 式探索）] + [在线建模台（Colab / Jupyter 式编码）] + [医学影像工具台] 的融合体**，针对肺结节多中心研究定制。

### 1.2 两轮设想的关系（重要）

客户提供的两份素材并非平行的两个功能，而是同一平台的**两个使用阶段**：

| 素材 | 定位 | 在工作流中的位置 |
|---|---|---|
| **第一轮 · Xena 截图** | 数据探索与可视化 | 数据准备阶段：浏览、筛选、可视化队列 |
| **第二轮 · A-D 描述** | AI 模型训练与实验 | 建模实验阶段：选数据 → 写代码 → 跑模型 → 看结果 |

两者构成上下游：在数据浏览器中选定队列 → 送入建模台进行训练/分析 → 结果回流到浏览器对比。**A-D 的建模台是更高级、更后端的阶段，它依赖于一个先就绪的数据层。**

### 1.3 A-D 四部分功能拆解

客户提出的"模型使用模块"四部分，我方理解如下：

#### ▎A. 研究任务 + 中心/医院选择（实验配置入口）

- **七类研究任务**：数据聚类、数据分类、图像标注、图像分割、疾病筛查、疾病诊断、疾病预测。
  - 我方理解：这是面向医学场景的**建模任务模板分类**，平台宜为每类任务预置标准算法骨架（如"图像分割"预置 U-Net 模板，"疾病预测"预置 Cox 回归 / 生存分析模板）。
- **四选的中心/医院**：对应多中心数据（省医、珠江-新桥等）。
  - 我方理解：不同中心的数据相互独立，需做数据权限隔离。

#### ▎B. 多模态数据选择（数据准备）

- **四类数据模态**：临床文本、基因、病理、影像。
  - 我方理解：与已设计的统一表对应——临床 ↔ `patient`/`visit_record`/`follow_up`；基因 ↔ `genetic_test`；病理 ↔ `pathology_specimen`/`ihc_result`；影像 ↔ `nodule_imaging`。
  - 用户选定模态后，平台应将该模态数据以可被 Python 代码消费的形式（如 DataFrame）注入执行环境。

#### ▎C. Python 脚本书写区（核心执行引擎）

- 浏览器内书写 Python 代码 → 提交后端 Python 3.10 解释器执行 → 返回结果。
- 我方理解：这是整个设想的技术核心，本质是「浏览器内嵌的在线 Python 建模环境」，体验应接近 Jupyter Notebook / Google Colab（支持变量持久化、内联图表输出、逐段执行）。

#### ▎D. 结果展示区（输出反馈）

- 显示代码执行的文本输出（stdout / 日志）和图表（matplotlib / ECharts 等）。
- 我方理解：图表既可能是 Python 端生成的静态图片，也可能是结构化数据由前端交互式渲染。

## 二、当前系统的能力现状（我方透明陈述）

为确保客户对实施基础有准确认知，我方如实说明系统当前能力与设想的差距：

| 能力维度 | 当前现状 | 对设想的支持度 |
|---|---|---|
| **平台底座** | ✅ 已具备完整的后台框架（FastAPI + Vue3 + ECharts + RBAC 权限 + Docker 部署） | 可直接承载新模块 |
| **医疗数据建模** | ⚠️ 仅有设计文档（`docs/unified_table_schema.md` 等），**尚未建表、未入库** | 🔴 阻断 A、B —— 数据层需先行落地 |
| **影像文件存储** | 🔴 **完全未规划**（当前仅有结构化测量值，无 CT/DICOM 影像文件方案） | 🔴 阻断"图像标注 / 图像分割"两类任务 |
| **Python 执行引擎** | 🟡 已有雏形：工作流引擎可执行用户提交的 Python 代码字符串（`exec`） | 🟡 可作为 MVP 底座，但生产级需升级（沙箱、交互式 Kernel） |
| **前端代码编辑器** | 🔴 暂无（需引入 Monaco Editor 等） | 🟡 需新增组件 |
| **AI 辅助能力** | ✅ 已集成 AI 助手（可对话） | ✅ 可扩展为"自然语言生成代码" |

**一句话总结**：平台骨架成熟，但医疗数据层、影像存储、安全执行环境三块基础设施尚需补建。**这是影响排期和范围的根本因素，而非 UI 层面的工作。**

## 三、需要客户确认的关键决策点

以下问题将带来 **5–10 倍工作量差异**，恳请客户在启动前明确拍板。按重要性排序：

### 🔴 决策点 1：影像数据的真实形态（影响最大）

"图像标注 / 图像分割"任务的数据基础是什么？

| 选项 | 含义 | 工作量 | 适用任务 |
|---|---|---|---|
| **甲. 真实 CT 影像文件（DICOM）** | 需引入医学影像存储服务（Orthanc 等）+ 三维查看器（OHIF / Cornerstone.js）+ 分割标注工具 | 极大 | 图像标注、图像分割 |
| **乙. 仅结构化影像指标** | 基于 `nodule_imaging` 表的测量值（长径 / CT 值 / 密度类型）做表格化机器学习 | 中等 | 数据分类、疾病预测 |
| **丙. 暂不做影像相关任务** | 首期聚焦临床 / 基因 / 病理三模态 | 小 | 七类任务中的五类 |

> **我方建议**：若影像是强需求，建议分期——首期选「乙」或「丙」先跑通全链路，影像能力作为二期专项。理由：医学影像栈（DICOM 服务 + 三维渲染 + 标注工具）本身就是一个独立的中型项目。

### 🔴 决策点 2：Python 执行的交互形态

C 部分的代码执行体验，期望达到什么程度？

| 选项 | 体验 | 实现方式 | 工作量 |
|---|---|---|---|
| **甲. 在线 Notebook（Jupyter 式）** | 逐段执行、变量持久化、图表内联、接近 Colab | 后端常驻 Jupyter Kernel + WebSocket | 中-高 |
| **乙. 提交脚本一次性执行** | 整段提交、一次性返回结果、无状态保持 | 复用现有 exec 引擎 | 低 |

> **我方建议**：若目标用户是研究者（需反复调参、探索性分析），强烈建议「甲」；若以运行预设模板为主，可选「乙」降低首期成本。**这是体验分水岭，请明确用户群体。**

### 🔴 决策点 3：目标用户与使用方式

平台的主要使用者是谁？这决定交互复杂度。

| 选项 | 用户画像 | 对代码能力的要求 | 平台侧重 |
|---|---|---|---|
| **甲. 临床医生 / 研究者** | 有医学背景，编程能力弱或无 | 平台应提供**模板 + 参数微调**为主，AI 辅助写代码 | 重模板化、低代码门槛 |
| **乙. 数据科学家 / 算法工程师** | 熟练 Python | 平台提供**自由编码环境** + 数据 SDK | 重开放性、灵活性 |
| **丙. 两者都有** | 混合团队 | 分层：模板入口 + 高级编码入口 | 工作量最大 |

> **我方建议**：明确主要用户群。若为医生群体，七类任务宜做成"选模板 → 选数据 → 调参数 → 一键运行"的低代码流程，而非让医生从零写 Python。

### 🟡 决策点 4：首期任务范围

七类任务是否首期全做？

> **我方建议**：首期聚焦 **2–3 类**，优先选择"仅需结构化数据、不依赖影像"的任务，以最快速度验证全链路：
> - **优先**：数据分类、疾病预测（仅需临床 + 基因 + 病理表格数据，pandas / sklearn 即可）
> - **次优先**：数据聚类、疾病筛查、疾病诊断
> - **延后**：图像标注、图像分割（依赖决策点 1 的影像方案）

### 🟡 决策点 5：数据规模与计算资源

- 各中心的数据量级？（几千份病例 / 数万份 / 十万级以上）——影响数据库选型（MySQL vs 列式存储）。
- 模型训练是否需要 **GPU**？若需要，需规划 GPU 资源池与调度。
- 同时在线写代码跑模型的研究者数量？——影响执行环境的隔离方案（单进程 vs 容器池）。

### 🟡 决策点 6：Python 版本一致性

客户提及后端 Python **3.10**，而当前系统后端要求 **≥3.11**。请确认：

- 是以 3.10 为准（需评估现有依赖兼容性），还是以系统现状 3.11+ 为准？
- 此差异是否影响特定算法库（如某些医学影像 / 深度学习库的版本要求）？

## 四、我方建议的实施路径

基于"先补基础设施、再渐进叠加能力"的原则，建议分阶段推进。**每阶段均可独立交付、独立验收：**

```
阶段 0  数据层落地（一切的前提）
   │
   ▼
阶段 1  MVP：跑通 A→B→C→D 全链路（聚焦结构化数据 + 2-3 类任务）
   │
   ├──────────────┐
   ▼              ▼
阶段 2a 体验升级    阶段 2b 影像能力
(在线Notebook)     (DICOM+分割标注)
   │              │
   ▼              ▼
阶段 3  AI 辅助 + 平台整合
```

| 阶段 | 目标 | 主要工作 | 前置依赖 |
|---|---|---|---|
| **阶段 0 · 数据层** | 让 A、B 有数据可挂 | 将 `docs/` 统一表转为数据库模型；导入多中心示例数据；建立数据访问 SDK | 无 |
| **阶段 1 · MVP** | 验证全链路可行 | 2-3 类任务模板 + 三模态数据接入 + Python 执行（复用 exec）+ Monaco 编辑器 + 图表回传 | 阶段 0 |
| **阶段 2a · 体验升级** | 接近 Colab 体验 | exec 升级为 Jupyter Kernel；增加安全沙箱；逐段执行与内联图表 | 阶段 1 |
| **阶段 2b · 影像能力** | 支持图像类任务 | DICOM 影像存储 + 三维查看器 + 分割标注工具 + U-Net 等模板 | 阶段 0 |
| **阶段 3 · AI 辅助** | 降低使用门槛 | 自然语言生成代码；结果智能解读；模板推荐 | 阶段 1 |

> **特别说明**：阶段 2a 与 2b 相互独立、可并行，取决于决策点 1、2 的答复。

## 五、风险提示

我方有责任在启动前如实提示以下风险，供客户决策参考：

1. **安全风险（C 部分）**：在线执行用户 Python 代码，若缺乏沙箱隔离，存在服务器被破坏、数据泄露的风险。**生产环境必须引入容器隔离或受限执行环境**，这部分工作量不可省略。

2. **影像栈复杂度（决策点 1）**：医学影像（DICOM）的存储、传输、三维渲染、标注是一套独立的技术栈，复杂度等同于一个中型项目。若首期纳入，将显著拉长交付周期。

3. **数据合规风险**：多中心医疗数据的汇聚、跨中心建模涉及数据合规与伦理审查，建议同步推进数据使用授权与脱敏流程。

4. **GPU 资源成本**：若涉及深度学习（图像分割等），需规划 GPU 硬件或云资源，属持续性成本。
