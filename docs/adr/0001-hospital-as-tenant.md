# ADR 0001: 医院与租户同一化

> 状态：已接受（已修订·2026-07-07）
> 日期：2026-07-07

## 背景

系统需要管理不同医院（省医、珠江-新桥等）的数据，并支持医院注册功能。系统已有一套完整的多租户体系（`sys_tenant` + `TenantMixin`），需要决定"医院"在领域模型中的定位。

## 选项

### 甲. 医院 = 租户（采用）

每注册一家医院即创建一个对应租户。医疗表含 `tenant_id` 字段。

**优点：**
- 复用全部现有基础设施（租户管理、用户-租户关联、配额、菜单权限）
- 医院特有操作（注册、映射配置、ETL 导入）以租户为锚点
- `tenant_id` 标记数据来源，支持按医院筛选

**缺点：**
- 医院概念被租户完全吸收，如果未来需要"一个租户管多家医院"需重构

### 乙. 医院是租户下的概念

一个租户管理多家医院，医院作为租户内的分类维度。

**缺点：**
- 需要新增 hospital 模型 + hospital_id 字段
- 现有 `data_scope` 基于部门层级，不直接支持医院级隔离
- 与现有架构的隔离机制不匹配

### 丙. 医院与租户无关

医院注册纯粹是数据元信息，不涉及多租户隔离。

**缺点：**
- 放弃现有租户隔离机制，需另建医院级权限体系
- 与平台已有的 RBAC + 多租户架构割裂

## 决策

采用甲：医院 = 租户。

核心理由：医院注册、映射配置、ETL 导入等操作以租户为锚点，复用全部现有管理机制。

## 附加说明（2026-07-07 修订）

> **重要**：`tenant_id` 在医疗业务表中作为**数据来源标记**，**不作为访问控制边界**。

- 所有登录用户可查询全部医院的医疗数据（当前阶段不脱敏）
- 前端按医院筛选仅为**查询维度切换**，不缩小用户的可见数据范围
- 完整需求书会定义脱敏规则和患者 ID 重编码方案；本方案暂不实现脱敏

即：`TenantMixin` 仍加在医疗表上，但 CRUD 查询层**不会按 tenant_id 做自动过滤**（这是与平台系统表的关键区别）。

## 后果

- `source_center` 字段保留用于历史数据兼容，新数据通过 `tenant_id` 关联
- 医院注册流程 = 租户创建流程
- 医院管理员角色是 `{tenant_code}_admin`（由 TenantService.create 自动创建），负责管理该医院的映射配置和 ETL 导入
- 医疗数据查询 API 接口接收可选的 `hospital_ids` 参数（多选），默认不过滤（返回全部）
