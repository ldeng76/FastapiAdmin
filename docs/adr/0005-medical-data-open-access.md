# ADR 0005: 医疗数据开放访问模型

> 状态：已接受
> 日期：2026-07-07

## 背景

初始设计假设"医院 A 的用户只能看医院 A 的数据"，规划了上下文切换机制（ADR 0001 原附加说明）。

但实际需求变为：所有登录用户可查看全部医院的医疗数据（当前阶段不脱敏），按医院筛选仅作为查询维度切换。完整需求书后续会定义脱敏规则和患者 ID 全局面编码方案。

## 决策

### 数据访问模型

| 维度 | 规则 |
|------|------|
| **可见范围** | 所有登录用户可见全部医院的医疗数据 |
| **按医院筛选** | 前端可选 1~N 家医院作为查询过滤条件；默认不过滤 |
| **当前阶段脱敏** | 不做任何脱敏处理 |
| **当前阶段 ID 编码** | 保留原始 patient_id，不重编码 |
| **未来扩展** | 完整需求书定义脱敏规则后，ETL 写入层增加脱敏转换；或在查询输出层增加脱敏序列化器 |

### 权限模型

| API 类型 | 权限规则 |
|----------|---------|
| 医疗数据查询 | 任意已认证用户均可（`medical:query` 是基础权限，所有角色默认拥有） |
| 医院管理/注册 | 仅超级管理员 |
| 映射配置/导入管理 | 仅超级管理员 + 该医院关联的租户管理员 |

### 对现有架构的影响

- `TenantMixin` 仍然加在医疗表上（`tenant_id` 作为数据来源列）
- 医疗数据查询**绕过** `CRUDBase.__tenant_condition()` 的租户过滤
- 实际做法：医疗表查询使用自定义 repository（不走 CRUDBase 的权限中间路径），或者显式跳过 tenant_id 过滤

> ⚠️ 这与平台系统表（dept/role/user 等）的行为不同——系统表仍按 `tenant_id` 自动过滤。医疗表是一个特殊的"平台级只读资源"——数据来源有归属，但读取对所有用户开放。

## 后果

- **前端**：顶部保留医院筛选下拉（多选），默认为空（=全部）
- **API**：`GET /patients?hospital_ids=1,2&...` 接收可选 IDs
- **ETL**：不做脱敏、不做 ID 重编码；完整需求书落地后回归修改
- **安全**：当前阶段若数据含敏感信息，需在部署层/网络层控制访问，不在应用层做隔离
